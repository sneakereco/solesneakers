# Sole Sneakers admin analytics

Date: November 25, 2026. Status: approved by the user, including the independent business/operational-data boundary, after the calendar/theme revisions and fresh builder check.

## Intent and user decisions

Give the store owner long-term visibility into the website's sales, customers, acquisition, product demand, payments, and checkout/fulfillment health, starting at launch. Black Friday prompted the request, but this is a permanent reporting feature, not a sale-only monitoring screen.

The user explicitly selected:

- An **Analytics page inside the Sole Sneakers admin**, with native charts, tables, filters, and drill-downs.
- **PostHog for everything it can support**; build the application integration and any verified capability gaps. Reports must be visible in the store's admin, rather than requiring staff to visit the PostHog website.
- Use the store owner's PostHog project and credentials. The earlier integration was configured for another developer's platform. Retain useful implementation, remove everything obsolete, and change the configured values.
- All proposed sales, orders, conversion, customer activity, product, profitability, and operational report categories, plus acquisition sources/campaigns and payment-method popularity.
- Fresh data from launch; no reconstruction or import of prelaunch visitor/order history. Since the site has not launched, legacy/test orders must not establish a customer's first real purchase.
- No giveaway-specific analytics.
- The seven-view mockup, with a **calendar for arbitrary start/end dates** replacing the fixed period dropdown, and the **existing website admin color theme**.

The full written design below includes the agent recommendations the user approved with this document. Implementation planning follows this approval; the execution method is selected after plan review.

## Approaches

1. **PostHog-first analytics, native admin presentation — selected by the user.** Send necessary, minimized behavior and commerce data to the owner's PostHog project. Use PostHog trends, funnels, retention, attribution, and SQL for reporting wherever possible. Application code owns reliable data delivery, definitions, access control, querying, caching, and presentation. This maximizes reuse but requires provider configuration, reporting queries, and explicit freshness/coverage handling.
2. **Hybrid reporting engine — considered, not selected.** PostHog for behavior and the application database for financial chart calculations. Keeps financial reporting independent of the analytics provider but duplicates reporting capabilities the user wants to use in PostHog.
3. **Fully custom analytics — considered, not selected.** Build collection, sessions, attribution, aggregation, and reporting ourselves. Gives full control but adds maintenance without serving the user's preference for PostHog.

PostHog does support custom revenue events, SQL insights, and an authenticated query API. These capabilities are sufficient to design PostHog-first reporting without promising a native Square revenue connector or a particular beta feature. The dedicated PostHog Revenue Analytics dashboard has been removed according to its current documentation; this design uses the underlying events/SQL/insights, not that dashboard.

- `src/styles/site.css` defines the existing admin palette: canvas `#f4f4f0`, white panels, ink `#09090b`, muted `#71717a`, neutral borders, light form controls, and black active controls. Reuse these tokens/components; the mockup's initial green appearance is not a new application theme.
- `src/app/admin/dashboard/page.tsx` currently calculates revenue from the paginated `/api/admin/orders` response; the endpoint defaults to 20 orders. This is not a storewide reporting calculation.
- `src/lib/measurement/client.ts`, `contract.ts`, `triggers.ts`, and `host-gate.ts`, with `docs/measurement/phase-a-browser-events.md`, implement four events: storefront viewed, product viewed, successful cart addition, and checkout started. They do not establish purchase completion, financial reporting, persistent returning visitors, or customer cohorts.
- The current measurement boundary deliberately disables automatic capture, replay, person profiles, and GeoIP enrichment, and uses session storage. Long-term reporting therefore requires an intentional, reviewed expansion of the contract rather than just changing a key.
- Orders already have subtotal, total, tax, shipping, refunds, fulfillment timestamps/status, and optional actual shipping cost. Order items have purchase snapshots and optional cost data. Square payment/refund records support authoritative outcomes. Missing components such as explicit pre-discount amounts, refund allocations, or processing fees must be recorded from their true sources.
- Existing money representations are mixed: helpers treat order totals as dollars and refund amounts as cents. All new reporting boundaries normalize and validate integer cents explicitly.

These are source findings, not evidence that the owner's PostHog project, secrets, ingestion, or hosted settings are configured or verified.

## Goals, non-goals, and failure conditions

Goals are trustworthy financial decomposition; clear customer/session/conversion definitions; acquisition linked to purchases where observable; understandable charts with useful filters; reliable delivery and recovery; and consistent admin styling.

Non-goals: giveaway dashboards or giveaway rule changes; importing historical data; replacing checkout/payment/shipping systems; accounting or tax filing; bank-payout reconciliation; predicted lifetime value; ad-platform integrations or return on ad spend without actual spend data; session replay/heatmaps; and individual browsing-surveillance pages.

The feature fails if it counts thank-you-page visits as authoritative sales, duplicates money after a webhook retry, mixes tax into product revenue/profit, silently drops unattributed orders from default totals, labels missing costs as zero, reports unavailable data as zero, changes purchase behavior, leaks credentials/PII, mixes staging with production, or leaves unused legacy measurement code behind.

Chart rules: use lines for change over time, bars for comparisons, a waterfall for additive money components, a histogram for order-value distribution, and a heatmap for cohorts. Do not use a pie where ranked bars are easier to compare. Label units/definitions and provide accessible table/text alternatives. Use real counts next to percentages; missing denominators produce `—`, not an invented rate. Color supplements labels and shape. Keep the application shell neutral; reserve restrained distinguishable chart colors for series and semantic success/error states.

The existing admin Overview can retain its operational role and show a small summary/link using the same reporting definitions. Replace its misleading paginated revenue calculation; do not build a second analytics dashboard or leave conflicting revenue definitions.

### Calendar, filters, exports, and report state

- Calendar permits an arbitrary start date and end date, including one-day ranges; show both selected dates. Provide direct date entry and quick presets inside the calendar as conveniences.
- Agent default: last 30 inclusive calendar days through today, `America/New_York` store timezone. UI dates are inclusive; server/provider boundaries are `[start local midnight, midnight after end)` converted correctly to UTC, including daylight-saving transitions. Never add a fixed 24 hours to compute a local next midnight.
- Compare with the immediately preceding equal number of local calendar days, with explicit dates. Current-day results are partial and labeled. Do not compare an in-progress period to a full period without indicating that difference.
- Disallow reversed, invalid, or future-ended ranges. Allow dates before first capture but label the available-data start and empty coverage; do not manufacture data or imply a prelaunch import. Choose chart bucket size appropriate to the range, with daily/weekly/monthly controls where useful.
- Preserve range, tab, comparison, and applicable filters in the URL. Reopening a link reproduces the report. Canceling a draft range leaves the applied range intact. Apply updates all applicable panels; discard stale responses from superseded filters.
- Global filters: device and acquisition source/channel/campaign where attribution exists. Report-specific filters: payment method; fulfillment; product/brand/category/size; new/returning customer; relevant order/refund status. Use the existing taxonomy and payment labels.
- Default financial totals include every qualifying confirmed order, including orders without behavior tracking. Applying a device/source filter changes financial scope to orders attributable to that segment; show that scope, unknown/unattributed counts, and attribution coverage. Never quietly describe a tracked subset as all sales. Filters that cannot apply to a metric must be clearly inapplicable rather than guessed.
- Export CSV uses the same applied range/filters/definitions and dataset as the visible report, with timezone, currency, data-as-of time, coverage, and report name. Protect spreadsheet consumers from formula injection. No raw customer contact/payment data is required in exports.
- Initial loading uses layout-shaped skeletons. Background updates preserve content but identify that it is updating. Distinguish no activity, no tracking history, missing provider configuration, unavailable component data, stale cached results, and provider/query errors. A failed analytics provider must not show successful zero sales.
- Agent freshness target: most completed commerce changes visible within five minutes under normal operation; recent visitor activity means events observed in the last five minutes, not a claim about all connected shoppers. Show observed ingestion/report timestamps and degradation.

## Metric definitions and money contract

USD is the initial report currency, matching the storefront. Preserve currency on every financial fact; never sum different currencies as though they were the same. Multi-currency conversion is outside initial scope.

| Metric                     | Definition                                                                                                                                                                                                                                                                                               |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Gross product sales        | Confirmed line quantities × pre-discount selling price snapshot. Not a current catalog price or original MSRP substituted after the sale.                                                                                                                                                                |
| Discounts                  | Explicit product/order merchandise discounts allocated to lines at purchase. A lower actual price is not an inferred historical discount.                                                                                                                                                                |
| Product refunds            | Completed, merchandise-allocated refunds; pending/failed refund attempts do not reduce sales.                                                                                                                                                                                                            |
| Net product sales          | Gross product sales − merchandise discounts − completed merchandise refunds. Tax and shipping are excluded.                                                                                                                                                                                              |
| Shipping collected, net    | Shipping charges after shipping discounts − completed shipping refunds.                                                                                                                                                                                                                                  |
| Tax collected, net         | Tax charged − completed refunded tax. This is reporting of recorded charges, not tax advice.                                                                                                                                                                                                             |
| Total collected, net       | Verified completed charges minus verified completed refunds; with fully allocated components this reconciles to net product sales + net shipping + net tax. Show unallocated refunds as a separate deduction when allocation is missing. Does not mean bank payout or accounting net profit.             |
| Confirmed orders           | Distinct website orders whose completion is confirmed by authoritative server processing, counted once. Fully/partially refunded orders remain in original completed-order counts; refunds are separate flows. Pending, failed, canceled-before-completion, and review/unresolved outcomes are excluded. |
| Paid payment transactions  | Confirmed positive-amount payment transactions. A valid zero-balance order has no invented payment instrument or payment attempt. No giveaway-specific report is added; valid standard order records retain their real aggregate effect.                                                                 |
| AOV                        | Confirmed merchandise amount after discounts, before refunds, tax, and shipping ÷ distinct confirmed orders. Label the denominator. Report net sales per order separately if useful; do not silently switch definitions.                                                                                 |
| Units / net units          | Confirmed quantities / confirmed quantities minus returned quantities. A partial monetary refund does not automatically mean an item was returned.                                                                                                                                                       |
| Gross product profit       | Net merchandise revenue on lines with recorded costs − applicable realized product COGS. Returned/resellable inventory and non-restocked refunds use actual inventory/accounting facts; do not assume every refund restocks. Show cost coverage by revenue and order/line counts.                        |
| Shipping contribution      | Net shipping collected − recorded label/fulfillment shipping costs, incorporating completed label credits when known. Missing costs remain unavailable.                                                                                                                                                  |
| Processing fees            | Actual provider-recorded fees, adjustments, and fee credits. Missing fees remain unavailable; do not fill them with an assumed percentage.                                                                                                                                                               |
| Unique visitors / sessions | PostHog's documented tracked visitor/session identities, scoped to consenting traffic and excluding known internal/test traffic. Anonymous visitors are browser-based estimates, not verified people.                                                                                                    |
| Active visitors            | Distinct observed tracked visitors active in the preceding five-minute window; independent of historical calendar totals and clearly labeled as such.                                                                                                                                                    |
| Store conversion           | Distinct tracked sessions with a confirmed purchase ÷ eligible tracked sessions in the same reporting window. Multiple orders in one session count once in the numerator.                                                                                                                                |
| Shopping funnel            | Ordered session → product view → successful cart addition → usable checkout → confirmed purchase, within the same tracked session. Show both start-relative and previous-step rates. Do not require a cart-page visit, since checkout can be entered directly.                                           |
| Checkout completion        | Purchasing sessions that reached usable checkout ÷ sessions reaching usable checkout. Server reservation expirations are a separate operational measure.                                                                                                                                                 |
| Purchasing customers       | Distinct store-scoped buyer keys with confirmed orders. New means first confirmed website purchase is within the selected period; returning means a confirmed website purchase predates it. This is separate from repeat browsing.                                                                       |
| Observed lifetime spend    | Net merchandise spend to date for the customer cohort selected by the report, explicitly labeled observed rather than predicted. Not selected-period spend disguised as lifetime value.                                                                                                                  |
| Payment success            | Successful resolved attempts ÷ all resolved attempts by method. Display attempt counts; pending/unknown outcomes are separate and retries do not create extra successful orders.                                                                                                                         |

Record sales on authoritative completion time and refunds on refund-completion time. Refunds issued now for earlier orders affect the current period, while an order-cohort drill-down can show lifetime outcomes for orders originally completed in a selected period. Label these two date bases and do not mix them within a chart. Product/source/cost snapshots are preserved even if catalog entries later change or are removed. Finite, exact integer cents and validated quantities are required at boundaries; formatting is display-only.

Agent decision for missing refund allocation: retain the verified refund total and show an explicit **unallocated refund** deduction/coverage warning. Product/tax/shipping net figures and profit must indicate incompleteness where affected; never guess proportional allocations or subtract the total twice. A later verified allocation revises the original refund fact and its original effective period. A new staff allocation workflow is not required for launch; existing refund actions should publish allocations when their actual source records establish them.

## PostHog data flow and reliability

### Behavior collection

Reuse the existing typed measurement helpers, host/environment gates, sanitization, and success-based triggers where useful. Expand the versioned contract to cover page/session entry, products, successful cart changes, usable checkout, consented purchase correlation, safe search-result counts, unavailable-size/stock signals, device category, and sanitized acquisition properties. Automatic form capture, unrestricted URLs/query strings, replay, and heatmaps remain off.

Behavior tracking starts only after optional analytics consent. Persistent anonymous IDs and first-discovery attribution are created only after consent; revoke stops collection and clears optional tracking identity/attribution. Support repeat visits with consented persistent IDs rather than session storage alone. Identify consenting signed-in users with opaque store-scoped IDs; do not send names/emails/addresses. Do not claim cross-device attribution for anonymous visitors. Internal admin, preview, automated test, and development activity must not pollute production reports. Bot exclusion is best effort and disclosed in definitions, not a guarantee every automated visit is detected.

Acquisition records source, medium/channel, campaign, link placement/content, landing pathname, and referring domain. Use sanitized UTM tags when present, otherwise a usable external referrer, otherwise direct/unknown. Keep first observed discovery and purchase-session source separately. Do not interpret every missing referrer as a typed URL, fabricate search keywords, or infer paid versus organic without reliable tags/platform data. No ad-click ID or ad-platform integration is required initially.

Collect search counts/result counts and recognized catalog/taxonomy concepts, not unrestricted visitor-entered search text. Device means coarse device type, not a fingerprint. Visitor GeoIP enrichment remains disabled; any future geography report can use appropriately minimized order delivery region, with a distinct label and scope.

### Commerce facts and the consent boundary

**Approved processing boundary:** send minimized server-side business facts for all confirmed website orders/refunds/costs **and operational payment/checkout attempts and outcomes, including failures and expirations**, to the owner's PostHog project independently of optional browser tracking. Complete financial totals and payment/checkout health counts cannot depend on a shopper accepting visitor analytics or completing an order. These facts must not enable browsing tracking for people who declined. This is the approved processing boundary, not a legal conclusion about consent requirements.

Commerce facts contain opaque order/line/refund/provider-event references, effective timestamps, currency, integer monetary components, product purchase snapshots, quantities, coarse fulfillment state, recorded costs/fees, and a store-scoped opaque purchasing-customer key needed for new/returning/lifetime purchase reporting. Keep raw email, name, address, phone, payment tokens, card details, IPs, and arbitrary provider payloads out. An opaque purchasing-customer key is pseudonymous, not a claim of anonymous data.

Operational failure/expiration facts use a server-generated opaque attempt/reservation reference, timestamp, coarse payment method/stage/outcome, and an allowlisted failure category. No raw provider error, request body, payment details, contact data, or browser identity is needed. Without visitor consent, do not attach browsing/session identity; count attempts and outcomes separately from the consented session funnel. A confirmed order or known customer is not required to record an operational attempt count.

Agent identity default: compute the buyer key inside the application from its transactional customer identity, using a keyed store-scoped mapping. Repeated guest orders can group by normalized transactional email inside the application; do not send that email or an unsalted email hash to PostHog, strip plus-tags, or guess identity from names/addresses/IPs. A browser-to-customer link is sent only when tracking consent is present. Verified signed-in identities can link consenting devices; guest grouping is a business-record estimate, not verified human identity.

If the owner later withdraws approval for independent business/operational-fact processing, that changes the implementation: use PostHog only for consented data and build complete financial and operational reporting in the application instead. Do not conflate this approved operational processing with the optional browser-consent gate.

### Durable publication and reporting

- The application database remains the authoritative transaction record. At transaction completion, refund completion, and relevant cost/fee/fulfillment updates, atomically record a minimized analytics publication job alongside the business state change. Provider responses and redirects alone are insufficient.
- Reuse an appropriate existing outbox facility if its ownership and capacity fit; otherwise add a feature-owned analytics outbox. Keep analytics network calls off the checkout critical path. Delivery failure must not block browsing, payments, orders, or refunds.
- Deliver commerce facts to PostHog through a bounded, retryable server-side drain. Stable fact IDs, monotonically increasing revisions where facts can change, effective timestamps, and source-event identity support retry/reconciliation. Do not assume PostHog's eventual event deduplication makes money queries immediately exact.
- Financial reporting queries must select one authoritative latest revision per fact ID before summing, and apply each completed refund/adjustment exactly once. Purchase-funnel outcomes deduplicate by confirmed order and tracked session. Tests must demonstrate duplicate/reordered deliveries cannot inflate amounts or conversions.
- Store source timestamps and observed ingestion/published timestamps separately. Late fees, shipping label credits, and refund allocation corrections update their proper fact/adjustment, not a second purchase. Corrections do not recapture a purchase as a new order.
- Prefer PostHog native insights for behavior and PostHog SQL/managed reporting views for financial/product/operational facts. The initial design uses event publication plus SQL because it does not require granting access to whole operational tables. A Postgres warehouse source is an available later option if justified and restricted to curated data; it is not required for this feature.
- An admin-only server reporting boundary executes allowlisted report/query definitions with validated typed filters. Do not accept arbitrary client-supplied SQL, query IDs, project IDs, or a selectable provider host. Return report-shaped aggregate results to native admin components.
- Use server-only minimally scoped query credentials for the owner's project. The public capture token is not a reporting secret. Check actual supported credential type/scopes in the owner's account; do not depend on a beta project key being available. Keep staging and production isolated, preferably separate PostHog projects.
- Cache and batch aggregate report queries, bound concurrency and query cost, and show cache/data timestamps. Agent default is a one-minute shared cache for recent summary queries and five minutes for heavier historical queries, tuned within the actual provider read budget. Never run one provider query per table row or issue unbounded queries on each keystroke.
- Source delivery lag, failed jobs, missing cost/refund/fee coverage, query failures, and attribution coverage are observable to maintainers/admins. Reconciliation compares provider-visible distinct fact totals with application business facts. Recover by retry/republication of the new system's durable facts, not by a prelaunch historical-import project.
- Retain financial and customer purchase reporting from production activation onward. Derive observed lifetime spend from the durable commerce ledger. Behavioral reporting covers observed history since activation within verified actual provider retention and any independently qualified archive. An archive can extend retention by choice. Verify actual provider retention and cost before launch. Expose missing intervals and expired metadata as unavailable. Paid features require owner approval.
