# Checkout and cart release hardening

Date: 2026-11-25

Status: Independently reviewed design for user approval. The user selected targeted hardening of the current release with selective reuse of reviewed fixes. A fresh builder check on November 25 reported “nothing important left.” Implementation, deployment and a Black Friday readiness claim are not approved by selecting that approach.

## Intent and scope

Make the existing paid-shopping release reliable before Black Friday, November 27, without waiting for the architecture rebuild. Address every finding BF-A01–BF-A13 in the [November 25 assessment](../../operations/2026-11-25-black-friday-checkout-cart-assessment.md), with a bounded repair, an explicit scope reconciliation, or a measurable release gate. This is a project spanning browser state, trusted database mutations, payment lifecycle, background recovery and release evidence.

The source assessment used application SHA `d8ce10191a294a0974be759bb2cb43b0bd980c53`. Subsequent local commits at design time changed documentation. The implementation must pin its own application/schema candidate and verify drift before porting any fix. Current staging and production workflow records differ; a successful workflow is not a fresh verification of the active alias, effective database permissions or provider behavior.

The user confirmed clear last-pair reservation feedback, explicit assurance of no charge when true, identification of the unavailable product/size in the cart, deeper resilience work, and option 1: harden the current release and reuse reviewed fixes. The defaults below are engineering proposals accepted only if this design is approved.

Coordinate with the separate [10,000-shopper hybrid staging load design](2026-11-25-black-friday-hybrid-load-design.md). Its workload/generator/telemetry project remains the capacity authority. Coordinate with the [specialty giveaway design](2026-11-25-specialty-giveaway-claims-design.md): prizes use a separate atomic claim flow, with a 1,000-submission contention test, not ordinary cart/payment/orders. Align older issues #37–#39 and #41 with those newer decisions before reporting readiness.

The parallel customer/admin UX remediation draft also covers receipts. This hardening package owns financial authority, receipt observation and purchased-unit consumption; that UX work consumes the resulting contract and owns its broader form/overlay/accessibility repairs and safe SDK initialization retry. Serialize overlapping changes to receipt, Cart and payment UI files; do not create another outcome poller or a second cart-clearing implementation. Include its affected browser regressions in integrated acceptance without expanding this package into the full admin UX project.

Goals: no oversells or duplicate accepted payments for one order; durable recovery after response loss or browser closure; truthful financial/refund history; customer cart edits preserved across identity changes and tabs; useful item-specific messages; bounded overload and backlog recovery; repeatable evidence for the exact shipped version.

Non-goals: wholesale architecture integration, tenant/schema contraction, platform/provider replacement, a new server-persisted shopping cart, visual redesign, changing ordinary pickup/shipping/tax rules, merging guest/account baskets, implementing the specialty feature in this package, or broad unrelated security cleanup. Preserve Square methods, address review, billing/contact requirements, cents-based server totals, consent gates and PR/staging/production-tag release gates.

Unacceptable outcomes include a faster response that hides lost work, customer-visible payment success without authorized server facts, retrying an unknown payment with a fresh key, releasing inventory that may be paid, deleting unrelated cart additions, weakening authorization to make a load test pass, and treating mock/provider-substituted results as live payment evidence.

## Cart persistence and identity

Preserve tab-local guest `sessionStorage` and account-specific `localStorage` keys. Preserve the existing deliberate guest/account separation on sign-in; do not silently merge or transfer baskets. Treat layout user data as bootstrap only. The latest verified session observation owns the active basket. A failed identity check is unavailable/denied, not a confirmed logout or guest session.

Each active storage connection has an immutable owner and generation. Every async read/validation/capture/bind/consume records its initiating owner, generation, revision and rendered/persisted snapshot. Recheck them immediately before applying a result and after acquiring a queued write lock. Navigation, identity/access changes, newer edits and relevant storage events invalidate old operations. An old completion cannot release a newer operation's token.

Serialize cooperating account writes across tabs using the reviewed account Web Lock. Re-read persisted bytes under that lock. Observe matching native storage key/area changes, including clears, and refresh or invalidate the displayed checkout. Detect legacy/raw writes through the final persisted-byte check. If required locking or storage access fails, show an actionable retry and reject the affected write rather than report success. Guest operations receive equivalent same-tab serialization.

Decode saved rows at runtime. Display salvageable legacy lines without rewriting damaged storage on observation. Report unusable lines, preserve unrelated original bytes until a deliberate repair/edit, and invalidate ineligible purchase proof before saving a repaired basket. Bound serialized sizes, row counts and purchase proof using the reviewed parser. A rejected add does not emit a successful-add analytic or toast. Validation transport/shape errors preserve the basket and display an unverified/retry state.

Server prices and stock remain authoritative. Client storage never authorizes a purchase. Account/password/OTP login, logout and session expiry must publish fresh identity observations; a failed logout must remain a failure. A changed identity cannot expose the prior account's basket, receipt or queued operation.

## Availability, validation and customer messages

Keep an unavailable row visible with its product/size, requested quantity and reason. Exclude it from payable totals and new captures. Keep valid rows and newer edits. Removing a row is the customer's explicit action; refreshing a cart must not silently remove unavailable rows or silently reduce quantity. Offer Recheck availability and Remove. Any price/quantity or eligible-item change invalidates the old quote and requires review before payment. Do not automatically charge the remaining items after one line loses stock.

Extend `/api/cart/validate` additively: retain legacy `items` and `removed` semantics for old clients, and add `contractVersion: 2` plus one typed `lineState` per requested product/variant. Each state identifies requested quantity, available quantity, availability (`available`, `reserved_by_other`, `sold_out`, `unavailable`) and canonical facts when available. The new Cart implementation reconciles these states with its captured request snapshot. Invalid/missing/ambiguous states cannot overwrite a basket; a legacy-only response produces conservative generic availability and preserves requested row identity. Client revisions are local concurrency guards, not trusted stock evidence.

Own holds must not look like another shopper's stock loss. Checkout may supply the active order reference and its order-bound credential to validation through a scoped adapter. The server validates ownership/access and active reservation state before crediting that order's held quantity. No client-supplied order ID alone adds availability. An expired/unknown financial attempt remains a recovery case; validation must not erase its original captured units or authorize a new payment from expired stock.

Prepare stock loss returns HTTP 409 with code `INVENTORY_CONFLICT`, affected product/variant IDs, requested/available quantities, a non-sensitive availability reason and `paymentState: not_submitted`. Resolve the failure in the authoritative allocation transaction with deterministic stock locking and all-or-nothing rollback; do not identify the losing item by an unprotected second stock read. Preserve no-store responses, basket limits and server price checks. Repeated preparation with the same owned key resumes one compatible order or returns an explicit conflict; a racing duplicate must not become a generic technical 503.

| Verified condition                                                         | Customer presentation and action                                                                                                                        |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Another order holds the last unit; this order has never dispatched payment | “Someone else just reserved the last pair of [product], size [size]. You haven't been charged.” Mark that row unavailable; review other available items |
| Sold out, inactive, missing, or exact reason cannot be established         | “[Product], size [size], is no longer available. You haven't been charged.” Use the no-charge sentence only for the same proven pre-payment condition   |
| Quantity/price changed                                                     | Identify the line and changed quantity/price; review updated total before a fresh submission                                                            |
| Validation/identity/storage unavailable                                    | Explain what could not be checked, preserve recoverable contents and offer Retry; do not call this sold out                                             |
| Local/server pre-dispatch failure                                          | Stable `PAYMENT_NOT_SUBMITTED`; retain the issued attempt and show a safe retry. This code is forbidden once dispatch may have occurred                 |
| Payment submitted, provider pending, response lost or outcome uncertain    | “We're confirming your payment. Don't pay again.” Check the existing order; no fresh charge action                                                      |
| Definitive declined/failed attempt with no unresolved prior attempt        | Explain decline; allow explicit retry only after server authorizes a new attempt                                                                        |
| Verified settlement                                                        | Show the receipt, then consume eligible original purchased units                                                                                        |
| Financial review, delayed, refunded or denied access                       | Show the specific verified state/support reference; do not claim a new successful payment or consume a pending basket                                   |

## Financial authority and durable attempts

### Trusted writes

Customers and anonymous clients retain only authorized reads of orders and related financial/line/reservation data. Revoke direct INSERT/UPDATE/DELETE/TRUNCATE and other unnecessary mutation privileges from those shared client roles; remove the broad customer `ALL` order policy. Audit child tables and callable SECURITY DEFINER operations for equivalent paths. A trigger that happens to reject one `paid` update is not authorization.

Both staff and customers use the shared `authenticated` database role today. Current fulfill/pickup routes construct session-client repositories, so move required staff mutations to narrow trusted server operations after `requireAdminApi` and input/transition validation before tightening grants. Test tracking, fulfillment, pickup, labels, refunds and resend flows. Never accept a client role/user ID as staff authorization or grant a broad public definer RPC to retain convenience.

### Attempt record and dispatch

Add a server-only `checkout_payment_attempts` record with order ID, attempt ID/sequence, method, exact integer amount/currency, cart/quote binding, stable Square idempotency key, canonical request fingerprint, dispatch state, provider payment ID when known, timestamps and structured recovery reason. Enforce one unresolved attempt per order using a database uniqueness constraint and order-row locking, not a Redis lock alone. Financial rows survive browser/key/token expiration.

States: `ready` (no gateway dispatch), `dispatch_started` (may have reached provider), `pending`, `unknown`, `succeeded`, `declined`, `canceled`, `review`. Final states preserve provider facts; an unknown attempt cannot be replaced merely because its worker lease or browser timeout expired.

1. Permit issuance finds/creates the order's eligible ready attempt under lock and stores its Square key before money can move. Repeated permits reference that same attempt; a fresh permit nonce does not mean a fresh payment. Keep the existing short-lived, atomically consumed Redis permit as admission protection, with attempt binding added.
2. Pay revalidates owner/access, order/attempt identity, totals, device context, required shipping/pickup/billing, live reservation and server policy. Then atomically changes the attempt from ready to dispatch_started, records its immutable request fingerprint and queues recovery in the same committed transaction. Only the winner may call CreatePayment. Do not hold SQL locks across external calls.
3. Persist the provider response/facts and resolve the same attempt under lock. Another permit or concurrent POST returns this attempt's known result/status URL; it cannot invoke the gateway again with a different key. The provider request and its retry key are fixed for the attempt.
4. Once dispatch may have happened, transport timeout, process crash, invalid response, token-used/idempotency errors, persistence failure and unknown SDK errors enter recovery. No new key or “not charged” promise follows from an absent payment ID. The background worker performs inquiry, not an unsolicited new CreatePayment.
5. A deliberate new payment attempt is allowed only after the prior attempt is proven declined/canceled with no pending/unknown/accepted attempt, and the order/reservation is still payable. A terminal failure before dispatch can safely retain or replace its unused ready attempt under the same guard. Any irreconcilable ambiguity becomes review with a visible support path.

Square documents same-request/same-key retries and rejects changing an already-used request; make payload equality part of our invariant rather than relying on the order ID alone. Do not assume an undocumented infinite key-retention period. Preserve the project's pinned API/SDK versions and verify actual Sandbox behavior before release. [Square idempotency](https://developer.squareup.com/docs/build-basics/common-api-patterns/idempotency), [CreatePayment](https://developer.squareup.com/reference/square/payments-api/create-payment).

Do not persist card details, raw payment source tokens or Turnstile tokens. A keyed source/request digest may bind an incoming submission without retaining its credential. An exact in-memory transport retry may use the same key/payload only through the guarded gateway policy; a closed browser is recovered by inquiry/webhooks and never needs its source token replayed. SDK automatic retries must be explicitly bounded and use that identical request.

Preparation remains independently idempotent. Bind a reused order to its verified account owner or original guest browser context, cart fingerprint and device. An idempotency key alone is not order-read authority. For a lost guest prepare response before an access token was received, use a server-issued Secure/HttpOnly/SameSite checkout-context cookie established by the existing quote response; persist its keyed context binding on the order. Reuse can mint access only for that original context. A new browser uses the existing secure order-access link; denial cannot reveal order details. Quote failures must not silently switch contexts for an already issued attempt.

## Provider facts, refunds and reservation lifecycle

Keep payment settlement, refund facts and fulfillment separate. Persist facts keyed by provider payment/refund IDs and recognized provider revisions; derive the compatible order projection transactionally. An event's delivery timestamp is not authority to reverse newer facts. An ordinary completed-payment repeat must not turn shipped/refunded/partially-refunded into paid or review. Refund totals are derived from distinct confirmed refund facts, not added again on every notification. Contradictory facts create a separate review flag/reason while retaining established settlement, refund and fulfillment history.

Verify signature/merchant/location/order/reference/currency/amount before applying facts. Deduplicate event IDs and make application idempotent by business object/version as well. Verify the expected finalized quote amount explicitly; do not reinterpret an arbitrary excess amount as new tax. A mismatch cannot authorize fulfillment. Where an event is insufficient or old, refresh the relevant provider object before projecting a change. The webhook envelope and operational payload must not become optional analytics.

Square does not guarantee webhook delivery order and may redeliver; design acceptance covers both. [Square webhook requirements](https://developer.squareup.com/docs/webhooks/overview).

The verified webhook receiver first stores a bounded durable inbox entry and pending work, then acknowledges receipt; persistence failure returns a retryable error. Use the existing webhook-event table with additive receipt/processing state where practical, plus a service-only bounded payload store if needed for recovery. Exact duplicate receipts cannot duplicate financial effects or notifications. Heavy provider refresh and email work is deferred to recoverable work, with the existing fast path available after durable acceptance.

Keep the existing 15-minute hold duration. Allocate every basket atomically and lock shared resources consistently: existing/new order first, then its attempt, then products in ID order, variants in ID order, reservations in ID order. New-order idempotency is resolved before stock allocation; a failed allocation rolls the new order and all stock updates back. No provider call occurs while those database locks are held. Align the product/variant suffix order with the separate specialty claim feature.

Expiration is an operation with proof, not a timestamp-only stock increment. Under a short lock mark an order expiry-pending and block new dispatch, then inquire/cancel through Square outside the transaction, then re-lock/recheck before releasing. A locally ready never-dispatched attempt can be retired. A possibly dispatched/approved/pending/paid attempt requires authoritative provider resolution; elapsed TTL, missing webhook or a single empty inquiry does not prove no charge. Confirmed cancellation must exclude a concurrent accepted payment before stock is restored. If this cannot be proved, retain the hold, schedule reconciliation and escalate; do not oversell to clear a queue. Validate the provider cancellation-versus-payment race in Sandbox.

Late settlement after release records money received, preserves the release history, raises review and blocks automatic fulfillment. Repeated/concurrent release or consume cannot restore or spend stock twice. A payment/refund replay after terminal settlement preserves that terminal financial history.

## Receipt observation and purchased-unit consumption

Use one typed outcome observer for processing, direct receipt visits and cancel/return paths. It validates the returned order ID, access context and runtime response shape, runs sequential abortable polling, and ends in a visible delayed/error/access state at its wall-clock deadline. Abort old work on order, credential, identity, navigation or retry changes. A 60-second initial observation ends with Check order status and support guidance, never an indefinite spinner. Status retries are GET-only.

Adopt the reviewed adaptive cadence: immediate read, one short early retry, then increasing intervals capped at five seconds with bounded jitter and no overlap. Reconciliation is shared with the background worker and rate-bounded per order; polling must not trigger an independent Square lookup on every request. Respect Retry-After and recover when a tab becomes visible. Preserve the same payment dialog host through submission, navigation and verified receipt.

Only a fresh authorized server result for the observed order can establish a receipt or purchased-line evidence. A same-layout in-memory handoff may be single-use and bound to the identical order/credential/session observation; persisted UI caches and URL presence cannot establish settlement. Order access failure never becomes “payment accepted.”

Cart exposes reviewed captureForCheckout, bindPreparedOrder and consumeConfirmedPurchase behavior. Before prepare, capture the original basket owner, revision and specific unit lineage using the rendered request and issued key. A lost response resumes that key/proof, never invents a new financial attempt. Bind the returned order before handing it to payment. After verified settlement, the authorized order reader supplies complete product/variant/quantity facts; Cart removes only surviving original units and records an idempotent receipt. Later additions, other lines, removed-and-readded identical SKUs, other account baskets and later attempts survive. Missing/corrupt/evicted proof preserves the basket and receipt; it never falls back to clearCart or best-guess subtraction.

Checkout housekeeping clears only the originating financial pair if the current owner/observation and purchased receipt still match. Keep device identity, unrelated/new credentials and guest address state. Multiple tabs observing the same purchase cannot consume twice or erase each other's newer attempt. Confirmed financial outcome remains usable even when basket storage is denied.

## Recovery throughput, admission and observability

Use PostgreSQL-backed recovery work rather than introducing a new external queue. A service-only `checkout_recovery_jobs` table contains work kind/order or provider reference, unique active-work key, next-attempt time, attempts, lease owner/expiry and scrubbed reason. Insert recovery work with prepare/payment/webhook transitions so a crash before scheduling after() cannot lose the obligation. A periodic sweeper also discovers legacy pending orders, expiring holds and unprocessed inbox entries; `after()` is a prompt optimization, not the durable scheduler. Installed Next documentation limits after() to its route/platform duration.

Claim due jobs with SKIP LOCKED and conditional lease ownership. Commit claims before network work. Reschedule failures individually with exponential backoff/jitter; unknown paid work moves to review/escalation without losing its recoverable facts. One poison job must not occupy every batch. Expiring a lease permits inquiry/processing again, never a second payment dispatch. Workers use bounded independent provider/SMTP concurrency, request deadlines and an elapsed-time stop budget; return unfinished work for another run and report partial failure honestly.

Proposed initial worker settings: one-minute schedule for recovery and notification fallback, batches of 50 with repeated claims until a 45-second budget, at most four concurrent external operations per dependency, 10-second external request deadline, 120-second leases, and retry delays from 5 seconds to five minutes with jitter. Concurrency budgets apply across overlapping worker invocations, not independently to each invocation. Use database-backed dependency leases or equivalent durable coordination for recovery so a Redis outage cannot remove the limits or halt recovery of existing financial obligations. These are starting configuration values for calibration, not throughput claims. Verify scheduler frequency, duration and quotas on the actual staging/production plan before implementation locks these values. If the current plan cannot support them, use a supported runner or obtain an explicit resource decision; a five-minute schedule must not be presented as meeting one-minute bounds. No paid upgrade is authorized by this design.

Retain the notification outbox and order-scoped prompt delivery. Lift the three-job fallback bottleneck through bounded repeated claims, not unbounded Promise.all. Keep confirmation/pickup jobs independent and audit known-sent mail. SMTP acceptance followed by a process crash before persistence is an ambiguous send: exact-once inbox delivery is not promised; preserve that ambiguity and avoid claiming the existing audit fully prevents it.

Replace the three-new-checkouts-per-IP rule with shopper/attempt-scoped admission plus a coarse calibrated IP safety ceiling. Proposed initial shopper limits: five new preparation keys per verified account or guest checkout context per 10 minutes, three gateway attempts per order per 30 minutes and five confirmed declines per shopper/hour; same-key resume/status/recovery do not consume a new-preparation allowance. Shared-IP counters alone must not reject designated legitimate shared-network scenarios. Distributed global admission and per-provider concurrency budgets protect expensive work before saturation; Redis failure blocks new money-moving attempts safely while durable recovery remains available.

The coarse IP threshold, global admission budget and provider budgets must be fixed from the actual workload/provider limits during calibration, versioned before the measured run, and validated through the real perimeter. They are load-suite configuration decisions with a release gate; do not merely delete bot, CSRF, Turnstile or WAF protection. Unexpected 403/429 responses are failures outside intentionally overloaded scenarios.

Use structured allowlisted lifecycle events with route templates, safe request/order/attempt/release references and durations. Never log credential-bearing URLs, tokens, permits, source IDs, cookies, addresses or raw provider request bodies, including inside nested values or error stacks. Sanitize existing proxy/order/error and optional analytics paths. Investigate verified historical exposure separately through protected access; no automatic deletion or broad credential rotation is implied.

Expose request p95/p99/errors/admission, gateway attempts per order, pending/unknown age, reservation expiry lag, queue depth/oldest due age, lease failures, webhook lag, notification age, worker heartbeat and DB lock/connection pressure. Avoid per-customer high-cardinality metric labels. Alerts identify a supportable order reference and runbook. The store owner names the release operator/on-call responder before promotion.

Operational switches are distinct: pause new checkouts stops new allocation while allowing safe completion/status/recovery of existing attempts; pause payment dispatch blocks new gateway calls while preserving inquiry/webhooks/reconciliation. Neither switch authorizes releasing ambiguous stock. Test both under load.

## Migration, rollout and rollback

Use additive migrations; preserve historical financial/customer records and migration history. Expand attempt, inbox/fact and recovery schemas and service-only operations first. Verify populated-copy preservation and effective permissions. Keep legacy permit/hash/address readers working; new permits bind an attempt. A legacy outstanding permit is resolved under the same order lock to an eligible existing attempt, or creates the one guarded attempt with its original Square key; a conflicting existing attempt returns status recovery, never a second key/charge.

Before promotion, pause new checkout allocation and record/drain or reconcile existing gateway dispatches. No fixed sleep alone establishes that old in-flight money operations have ended. Deploy compatible trusted staff writes and the receiver/worker/application together, then enforce client mutation restrictions and enable guarded dispatch. Signed webhook receipts and recovery remain durable through the cutover; if durable receipt cannot be guaranteed, return retryable failure instead of acknowledging and dropping an event. Verify old browser request contracts fail safely or resume under the new server guards.

Backfill/enqueue legacy pending or suspicious orders conservatively. Never mark an old attempt safe to retry, cancel a provider payment or release stock solely to make a migration/health check green. Any ambiguous preexisting order must have a reconciled outcome or documented review with protected stock before opening traffic. Restore tests must prove data and job continuity.

Stage through synthetic smoke, limited real Sandbox verification, increasing load and full acceptance. Preserve PR staging and production tag gates; this design authorizes neither merge nor promotion. Store opening time stays a store-owner decision. On failure pause new attempts, preserve inbox/attempt/outbox records and let safe recovery continue.
