## Global Constraints

- Preserve current branding, policies, shipping/pickup rules, supported payment methods, security controls, consent choices and the agreed cart identity policy. Do not invent a new guest/account merge rule.
- Keep staging/production release gates intact. This design authorizes no deployment, migration, provider charge, label purchase, refund, order email or production-data modification.
- Do not introduce a full component framework, analytics provider, Figma file, new design service or redesigned business flow for this repair program.
- Every admitted action must acknowledge touch, mouse or keyboard activation immediately, communicate any ongoing work and provide a truthful result. Every asynchronous content region must have an intentional loading presentation on mobile and desktop.
- Skeletons are non-interactive and hidden from the accessibility tree; give the containing region a useful busy state and a single concise loading/status announcement.
- Never manufacture success or delay completed content just to display a loader.
- Preserve required hard-document navigation into checkout and any associated security/provider headers.
- A skeleton or old total cannot enable an unverified payment. Keep initialization retries separate from ambiguous payment recovery.
- Keep feature code together in the existing feature folders. This worktree has no `.codegraph/`; do not query the parent checkout's index for this branch.

## Review Focus

1. Two taps or Enter plus tap before a pending render must not duplicate a mutation; Tasks 1, 4, 5 and 7 hold the response and assert one command.
2. Cached/URL receipt data and a late response for another identity must never establish purchase authority or consume a new basket; Task 6 tests replay, lineage, identity and storage-write failure.
3. Loading boundaries must not flash signed-out/empty/zero data, expose protected content or stop provider challenges receiving focus; Tasks 3, 4, 5, 7 and 8 exercise those transitions.
4. Escape in a select or nested modal must close only its owner and return focus correctly; Task 2 tests nested/native surfaces and RdkSelect keyboard behavior.
5. Slow/failed/refreshed data must preserve input/current usable content and exit busy state with an actionable result; Tasks 3–8 test failures, cancellation, stale responses and reduced motion.

## File ownership and interfaces

- Shared primitives live under `src/components/ui`; shared HTTP failure classification under `src/lib/http`. Request ownership stays with features.
- Feature skeletons live under the corresponding existing `store`, `cart`, `account`, `admin`, `auth` and `checkout` component folders. Route `loading.tsx` files import those compositions.
- `ActionButton` preserves native button props and caller classes, with `pending?: boolean`, `pendingLabel?: string`, `variant?: "primary" | "secondary" | "ghost" | "danger"`; its default must not override existing feature appearance.
- `useAsyncAction()` returns `{ pending: boolean, run: <T>(operation: () => Promise<T>) => Promise<T | undefined> }`. It synchronously admits one operation, resets in finally and rethrows errors to feature handling. Duplicate admission is a no-op, not a second request.
- `Skeleton({className?})`, `LoadingState({label,children,className?})`, `RequestError({message,onRetry?,retrying?,signInHref?})`, and `readJsonResponse<T>(response: Response, fallbackMessage: string): Promise<T>`. The HTTP helper throws a typed `ResponseError` carrying status; UI copy remains safe/feature appropriate.
- Task 3 HTTP helpers in `src/lib/http/request-deadline.ts`: `withRequestDeadline<T>(request: (signal: AbortSignal) => Promise<T>, parentSignal?: AbortSignal)` and GET-only `fetchJsonWithDeadline<T>(url: string, fallbackMessage: string, parentSignal: AbortSignal)`. Both provide the existing 15-second abort deadline; the GET helper covers body consumption. They propagate caller cancellation and dispose timers/listeners after settlement without requiring AbortSignal.any/timeout. The current generic helper requires its callback to honor the provided signal; noncooperative-callback expiry is a deferred review item and must be resolved before relying on it for opaque operations. Reuse for owned reads; mutations retain feature-specific ambiguity/recovery behavior.
- `FeedbackLink` in `src/components/ui/FeedbackLink.tsx` forwards native Next Link props/ref, including the legacy single-child path; current normal links compose `useLinkStatus` feedback without disabling prefetch. Preserve its native modifier/new-tab semantics.
- Task 4 session contract: `readServerSession()` returns a verified session, confirmed null, or throws an unavailable lookup; the legacy `getServerSession()` guard still fails closed. Context retains `refreshSession(): Promise<void>`, `user` and `role`, and adds `isSessionUnavailable` and `hasRefreshed` alongside `isLoading`. Null is confirmed guest only when loading/unavailability are false. Task 6 adds isIdentityCurrent(expectedOwner: string | null): boolean, a synchronous command precondition that rejects active refresh, unresolved/unavailable identity and a mismatched latest committed owner; cart checks it at admission and after lock acquisition. Server props accept optional `initialUnavailable` and opaque per-read `serverReadId`; new confirmed snapshots replace identity and invalidate old reads, while unavailable snapshots retain known identity. `X-Account-Owner` is an optional restrictive account request precondition, never authorization or a record selector; mismatches return409 and require fresh owner recovery.
- Task 4 account result contracts: address POST returns canonical `address` plus `addresses` when the list refresh succeeds; a missing list is recoverable independently of the confirmed write. Default retry adds `savedAddressId` and all last-seen fields; server resolves the row for the current authenticated owner and returns412 `saved_address_changed` before writes if missing/changed. Recovery verification returns `recoveryOwnerId` after existing MFA decisions; each password write sends it and must match its current authenticated owner. This is an intent precondition, with existing AuthService/MFA authorization unchanged.
- `ModalPortal` retains its existing props and adds `label?`, `labelledBy?`, `describedBy?`, `placement?: "center" | "left" | "right"`, `initialFocusRef?`, and additive `invoker?: HTMLElement | null` captured from the actual launcher. It supplies one native named modal surface, correct body scroll lifecycle, Escape/backdrop handling and focus restoration. Consumers stop adding a second dialog role.
- Overlay launchers pass their actual element through the optional `invoker` prop. Navbar `openCart`/`openSearch` CustomEvents carry `detail: { invoker }`. Plain events remain valid for programmatic opens, using prior-active fallback. Preserve this ownership when migrating controls.
- `RdkSelect` additionally accepts `id?`, `aria-label?` and `aria-labelledby?` for the real trigger so later feature-label repairs can associate visible field labels without duplicating select implementations.
- Task 5 adds `ConfirmDialog.pending?: boolean`, disabling dismissal and all confirmation controls while retaining modal keyboard focus. Transaction detail has optional `emailLogsAvailable?: boolean`; unknown audit availability must not become “not sent.” The existing admin products GET accepts one exact identity, `exactId` or `exactSku`, returning `{product: {id,name,archived_at,variants:[{sku}]} | null}` from an uncached tenant-scoped read including archived products and all sibling SKUs. Clean absence differs from a failed read. Label HTTP502 `shipping_label_purchased_without_tracking` is positive purchase evidence with a support reference. `transitionProviderCheck(key, expected, next): boolean` verifies tab persistence for label admission and recovery; only a durably verified unknown state permits explicit negative operator acknowledgement. These tab guards do not coordinate other devices or survive manual browser-data deletion.
- Task 7 adds optional `CheckoutPageData.customer.ownerId?: string | null`; the real producer always emits its verified user ID or confirmed guest null and uses strict `readServerSession`. Non-guest data without an owner fails closed. Client checkout retains same-owner drafts during pending/unavailable identity but gates quote/preparation/payment, and hides previous private customer fields after a confirmed owner mismatch until fresh checkout data is loaded. Existing financial/provider attempts retain their own lifecycle. The real checkout supplies `SquarePaymentMethods.reviewOwner?: {verified: boolean; isCurrent(): boolean}` to gate app-owned private review rendering and continuations independently of native provider challenges.
- Task 7 extends `startCheckoutOrderPolling(orderId, token, onState, {reconcile?: boolean} = {})`; its existing default reconciles during processing, while direct receipts explicitly use `{reconcile:false}` for read-only access. Both use the serialized 60-second deadline and validate matching paid evidence. `clearCheckoutAttempt(key): void` removes tab attempt/fingerprint only if the captured key still matches, without changing payment outcome on local cleanup failure.
- Cart ownership remains guest sessionStorage (`rdk_cart_session`) versus per-user localStorage (`rdk_cart_user_<id>`). Persist cart changes and replay-safe unit lineage atomically, preserving compatibility with existing array readers/writers and legacy migration. Versioned per-line metadata is allowed; any envelope must prove safety for already-open clients.
- Task 6 adds optional authoritative `purchasedItems?: Array<{productId:string;variantId:string;quantity:number}>` and `customerId?: string | null` to `OrderStatusResponse`; authenticated/token authorization remains unchanged. Older/mock responses without this evidence must not mutate a cart.
- Task 6 exposes `captureCheckoutSnapshot(): CartCheckoutSnapshot`, `bindCheckoutSnapshot(orderId: string, snapshot: CartCheckoutSnapshot): Promise<boolean>`, and `consumeConfirmedOrder(order: OrderStatusResponse, onUpdateUnavailable?: () => void): Promise<boolean>` through the cart context; exact opaque snapshot type is owned by `src/lib/cart/checkout-snapshot.ts`. Capture rejects a stale/unavailable owner or revision before preparation. Binding persists the first immutable order snapshot under the account's cooperative lock in account-scoped localStorage (guest bindings stay in sessionStorage); failure preserves the basket and must not automatically start a new payment attempt. Cart mutation methods return `Promise<boolean>` so upgraded shared-storage writers can serialize through per-key Web Locks; expected storage failures resolve false and surface a local error. Acknowledgement callers await durable success. Cooperative locks do not govern legacy clients, whose observed noncanonical serialization invalidates their lineage conservatively. Task 7 captures before preparation awaits, awaits binding only for a newly prepared order and awaits trusted consumption. Only an explicit `reused: false` preparation may establish a fresh binding; reused or missing flags retain an original binding if present, otherwise preserve the basket. Cart context also exposes `validationStatus: "idle" | "loading" | "error"` and `retryValidation(): void` so cart validation has visible, recoverable regional feedback. It also exposes `hasCartView: boolean` for retained current-owner content independently of `isReady`, plus `writePending: boolean` and `writeError: string | null`. Pending/unavailable identity keeps readiness false while retaining only that known owner’s view; confirmed owner changes must not expose the previous basket.
