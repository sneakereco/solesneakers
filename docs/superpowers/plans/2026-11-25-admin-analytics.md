# Sole Sneakers Admin Analytics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the seven-view analytics page inside Sole Sneakers admin, powered by the owner's PostHog project, with complete financial/operational reporting and consented visitor analytics from launch.

**Architecture:** Keep feature code in `src/Modules/Analytics/Source/Features/<Feature>` and unit tests in `src/Modules/Analytics/Tests/Features/<Feature>`. Transactional source snapshots and a private outbox publish minimized versioned facts to PostHog; consented browser events supply visitor/session attribution. Server-only PostHog queries return typed report data to native admin components, with caching, coverage, safe exports, and provider-independent transaction authority.

**Tech Stack:** Existing Node `^24.14.1`, Next.js `^16.3.3`, React `^19.2.0`, TypeScript, Supabase/PostgreSQL 17, Square, Shippo, Upstash Redis, PostHog JS `1.433.3`, Jest, and Playwright. Add `@date-fns/tz` for zoned boundaries and `@daypicker/react` for the calendar, pinning resolved compatible versions in `package.json` and the existing lockfile. Use feature-owned SVG/CSS charts with accessible data tables; no second analytics engine or chart framework is required.

**Spec:** [Approved admin analytics design](../specs/2026-11-25-admin-analytics-design.md). Read both documents before execution. The calendar mockup is `.superpowers/brainstorm/2026-11-25-admin-analytics/content/analytics-v4-calendar.html`; it is visual reference, not production code.

## Global Constraints

- **PostHog for everything it can support**; build the application integration and any verified capability gaps.
- **Analytics page inside the Sole Sneakers admin**; all seven agreed report views are required.
- **calendar for arbitrary start/end dates**; `America/New_York`, last 30 inclusive days by default, exclusive next-local-midnight query boundaries.
- Existing admin theme: canvas `#f4f4f0`, white panels, ink `#09090b`, muted `#71717a`, neutral borders, black active controls.
- **No giveaway-specific analytics** and no giveaway/purchase-rule changes; no historical imports or legacy/test customer classification.
- Approved: minimized server business and operational facts independent of optional behavior consent; pseudonymous buyer grouping. Optional browser capture, persistence, identity linkage, and acquisition history remain consent-gated and revocable.
- Preserve exact integer cents, original purchase snapshots, completed-refund allocations, explicit missing-data coverage, and original effective dates. Do not treat unknown as zero.
- All-since-launch financial history and at least 24 months of behavioral history; observed lifetime value, not prediction.
- Five-minute normal commerce freshness target; same-session funnels; completion/refund-time financial flows.
- No new replay, GeoIP, ad-spend integration, paid-plan action, staff refund-allocation workflow, or historical import.
- Preserve staging PR and production tag/release gates. Production activation accompanies public launch; missing owner credentials/hosted verification are explicit release gaps, not permission to claim completion.
- Read the installed Next.js guides before production code: `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md`, `05-server-and-client-components.md`, and the applicable cookies/after/cache guidance. Route handlers are not cached by default; authenticated reports must not become public/static cached responses.

## Review Focus

1. Eastern Time DST, leap days, single-day selections, and canceled drafts must keep the displayed dates, query instants, comparison, and export consistent: Tasks 1 and 10 pin these cases.
2. Duplicate/reordered publications, zero-balance completion, and partial/unallocated refunds must not inflate money, orders, or purchasing sessions: Tasks 3, 6, and 7 exercise distinct facts in a real local database and provider-query fixtures.
3. A guest declining/revoking analytics, then attempting payment or later signing in, must retain complete business reporting without a browsing identity: Tasks 4, 5, and 8 exercise the consent receipt and identity boundary.
4. Rapid filter changes, unattributed orders, cross-project caches, and malicious query/export inputs must not show another scope's totals or expose credentials: Tasks 9 and 10 pin these cases.
5. Missing/late costs, fees, refund allocation, deleted products, and expired provider history must remain visible as incomplete coverage rather than zero profit or fabricated history: Tasks 5–8 and 14 exercise these cases.

**Files:** Create `ReportContract/{types,calendar-range,filters,money}.ts`; tests `Tests/Features/ReportContract/{calendar-range,filters,money}.test.ts`; modify `package.json` and the existing lockfile for `@date-fns/tz`.

**Interfaces:** Produce `ReportId = "overview" | "sales" | "customers" | "acquisition" | "products" | "payments" | "health"`; `CalendarRange = {from:string; to:string; timezone:"America/New_York"}`; `resolveCalendarRange(range: CalendarRange, now: Date): ResolvedRange` containing `from`, `to`, `startInclusive`, `endExclusive`, `calendarDays`, `comparisonStartInclusive`, `comparisonEndExclusive`, and `partial`; `parseReportRequest(input: URLSearchParams, now: Date): ReportRequest`; `toCents(value:number|string,unit:"dollars"|"cents"):number`; and `MoneyValue = {cents:number|null; complete:boolean; missingCount:number}`. Derived money permits negative net periods/profit. Source charges/fees/quantities have their own nonnegative constraints; conversion never silently rounds fractional cents.

`ReportRequest` contains `report`, `range`, `compare:boolean`, `bucket:"day"|"week"|"month"`, `dateBasis:"activity"|"order-cohort"`, `page:number`, `pageSize:number` (default 50, maximum 100), `sort:string` chosen from a report-specific allowlist, and optional `device:"mobile"|"desktop"|"tablet"|"unknown"`, `source`, `channel`, `campaign` (bounded sanitized slugs), `paymentMethod:"card"|"applePay"|"googlePay"|"afterpay"|"cashAppPay"|"unknown"`, `fulfillment:"ship"|"pickup"`, UUID product/variant/taxonomy IDs, `customer:"new"|"returning"`, and an allowed status. Missing filters mean all, while explicit unknown is a real unmatched bucket. No SQL/project/provider field is accepted. Every paginated table returns matching total count and stable tie-breaking sort; chart totals are not derived from the first table page.

`ReportEnvelope<T>` contains `data:T`, `range`, `scope`, `asOf`, `ingestionAsOf`, `datasetStartedAt`, `coverage`, and `state: "ready"|"empty"|"unconfigured"|"unavailable"|"stale"`. `ReportDataMap` has the seven report DTOs defined by the output fields in Tasks 7–8; define shared `TimeBucket`, `FunnelStep`, `SourceRow`, `ProductRow`, `PaymentRow`, `CustomerCohort`, and `CoverageIssue` types here rather than casting raw provider rows in views.
