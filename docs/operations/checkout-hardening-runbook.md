## Read the checkout health signal

The existing authenticated cron reader can GET `/api/cron/checkout-health` with the server's cron bearer credential in the Authorization header. Read via the approved protected operations client. Each read takes a current PostgreSQL snapshot and returns `Cache-Control: no-store`. Public `/api/healthz` remains the process liveness probe. Existing `/api/readyz` checks application dependencies. Checkout recovery readiness comes from the protected endpoint.

- HTTP 200 means the snapshot passed the configured local alert checks. HTTP 401 means authorization failed. HTTP 503 with `health_unavailable` means the reader could not verify the snapshot. Check the protected probe credentials, migration version and DB connection. Do not infer an empty queue from that response.
- `workerLastSeenAt` is the earlier of the two successful end-of-sweep heartbeats. A missing worker makes the aggregate null. Compare the individual clocks to `observedAt`. Startup, a health poll and order-scoped prompt mail delivery do not refresh either scheduled worker.
- `manual_review` means a recovery job, notification or financial review marker requires investigation. Review count is obligations, so one order can have several. Use `correlation.alertOrderIds[alert]` for the specific triggering condition. The protected response retains `correlation.reviewOrderId` for review lookups. Unknown and pending payments, expired holds, overdue local recovery jobs, unsent mail and expired local leases each use the corresponding durable order foreign key. An older unbound queue job cannot implicate a younger local order below the alert threshold. An event-only job can have no verified order link. Investigate that receipt within restricted operations. Preserve unknown money, stock, immutable attempts and ambiguous mail handoffs. Reconcile independent payment facts and sent audit before choosing an authorized resolution.
- The initial local thresholds are more than ten minutes for the older heartbeat, unknown dispatch and oldest unsent mail, more than fifteen minutes for pending payments and more than five minutes for due recovery work, expired active holds and unprocessed Square webhooks. Any review obligation, expired lease or current database lock waiter raises an alert. Database connections at or above 80% of PostgreSQL `max_connections` raise an alert. These thresholds require calibration against the qualified workload.
- Use `queueDepth` for pending plus review recovery rows and `notificationDepth` for unsent mail including review. Oldest due counts already-due pending work, including an owned job in progress. Unknown age includes started dispatches and unknown attempts. Pending age uses the payment attempt's dispatch or creation time. Active lease gauges count unexpired Square, Shippo and SMTP slots. Expired leases include stale recovery, mail and dependency claims. Review mail safely through its outbox row and the independent sent audit. An authenticated refusal and ambiguous SMTP handoff have different retry rules.
- Connection pressure is the current PostgreSQL cluster backend count against the cluster connection limit. Lock waits count ungranted locks held up in this database at observation time. Managed pooler limits, platform quotas, historical lock durations, and worker capacity/fairness need deployment-side measurement.
- Inspect `pauseNewCheckouts` and `pausePaymentDispatch` independently. Missing/invalid versioned admission configuration reports `foreground_admission_unconfigured` and returns HTTP 503. New expensive work is gated while the existing database recovery paths retain four slots per dependency. With a valid configuration, compare its canonical JSON SHA-256, version, IP/global budgets and shared Square/Shippo caps to the run manifest. SMTP retains four slots. On a cap reduction, drain older writers and verify the deployed revisions. Avoid releasing holds or retrying ambiguous payments as an alert response.

`checkout_admission` counts decisions by phase, operation, outcome and bounded denial reason. Preflight and locked dispatch-authority results have distinct series. A pause, quota refusal or observed follower creates zero new SDK calls. Address validation and coarse protection are distinct operations. The later distinct-key check retains the same request's single coarse charge. Group proxy denials and fail-open outcomes separately. Persisted dispatch-start and actual SDK-call counts have different crash boundaries. The provider must independently qualify receipt and charging behavior. Keep lifecycle attempt state and observed follower decisions outside retry counters.
