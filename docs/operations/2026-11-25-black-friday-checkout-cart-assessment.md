# Black Friday checkout and cart assessment — November 25, 2026

The audited release is not ready for a Black Friday reliability sign-off. Scarce-stock allocation held up in bounded local PostgreSQL checks, but customer basket state, financial authority, payment retries, refund history, feedback and recovery have material gaps. Capacity at either the issue tracker's 2,000 active shoppers or the newer load design's 10,000 has not been demonstrated.

This is an investigation and repair-sequencing proposal, not an approved implementation design or completion of the broader architecture assessment in issue #44. Product behavior has not been changed by this assessment.

## Confirmed customer requirement

When another shopper reserves the last pair before payment submission, explain that clearly, identify the product and size, and state that the losing shopper has not been charged. The cart should retain enough information to identify the unavailable line and exclude it from the payable total, while preserving the other lines and quantities.

The server must distinguish a confirmed reservation conflict from sold-out, inactive or otherwise unavailable inventory. Zero available stock alone does not establish that somebody just reserved it. “You have not been charged” is appropriate only when the payment has not been submitted, or a definitive provider result establishes that fact. A lost payment response needs an honest checking/pending state and recovery of the existing attempt.

## Capacity and recovery limits

- The successful 32-transaction test verifies one database contention scenario. It does not measure hosted response latency, browser admission, Supabase connection limits, serverless concurrency, Redis/Square/Shippo quotas or 2,000 active shoppers.
- The notification fallback claims three jobs every five minutes: **36 jobs/hour** if each run succeeds and completes its claimed work. An order-scoped prompt path separately attempts two jobs and must be preserved. The fallback figure is not the total normal send rate. A 360-job outage backlog would need at least ten scheduled hours through that fallback alone.
- The expiry job reads at most 50 pending expired orders every five minutes: a nominal **600 candidates/hour**, before provider calls, errors and the 60-second runtime deadline. Failed early candidates remain eligible; cleanup fairness and oldest-hold age need attention.
- Status polling normally approaches one request per two seconds per pending browser after its initial read. If all 2,000 shoppers were pending simultaneously, that is roughly 1,000 status requests/second before reconciliation fan-out. This is a worst-case planning envelope, not a measured load or an assumption that every shopper pays.
- At the newer design's 10,000 shoppers, the equivalent all-pending envelope would be approximately 5,000 status requests/second. The real workload must specify the pending-checkout fraction and think times rather than equating shoppers with requests/second.
- Normal cart storage reads are local; replacing them with database writes is not inherently a resilience improvement. The demonstrated problems concern ownership, revisions, persistence failure reporting and coordination between displayed basket, validation and financial attempts.
- Existing CI runs unit/integration suites, measurement browser checks and a build. It does not run the database contention suite, the complete checkout browser suite or a k6 acceptance suite. Passing CI therefore does not establish these release properties.

## Proposed repair sequence

1. Select and pin the actual release candidate. Reconcile the latest reviewed Cart/Checkout work with that candidate; keep source, schema and deployment evidence attached to its SHA.
2. Restrict customer financial/order writes, preserve terminal payment/refund facts, and establish durable single-attempt payment ownership and recovery before another charge can be submitted.
3. Complete cart revision/identity/tab protection and verified, order-bound purchase consumption. Preserve newer/unrelated basket edits, access recovery and the chosen guest/account separation policy.
4. Add truthful, item-specific stock conflict states from preparation through cart and checkout, including price/quantity changes, validation failures and unknown payments. Stock loss before payment must not become a technical 503.
5. Make reconciliation independent of an open browser. Bound retries, deadlines and worker concurrency; prevent recovery starvation and measure expiration/notification backlog drain. Review shared-IP admission without weakening payment/security controls indiscriminately.
6. Reconcile historical giveaway issues with the newer specialty draft. Keep its separate atomic address/Instagram claims and 1,000-submission contention gate coordinated with the shopping load effort; do not expand ordinary checkout merely to implement that separate feature.
7. Exercise the pinned candidate on isolated production-like staging. Include stock-one bursts, multi-item rollback, duplicate/response-lost attempts, release-versus-pay, reordered payment/refund events, closed tabs, auth changes, denied storage and network/provider failures.
8. Reconcile issue #41 with the newer hybrid load design's 10,000-shopper target, then run that capacity gate: realistic traffic ramp/hold, hot-SKU burst, above-target spike, soak, shared-NAT admission and dependency recovery, with measured p95/p99, technical failure rate, DB connections/locks, provider limits and oldest unresolved work. Assert zero oversells/duplicate accepted claims/duplicate fulfillment and preserve payment facts after every run.

The existing [#43 work program](https://github.com/sneakereco/solesneakers/issues/43) and [#44 assessment](https://github.com/sneakereco/solesneakers/issues/44) already cover this work. Issues #25, #26, #32, #34, #36 and #41 were fetched individually and remained open. No duplicate issues or external comments were created.
